# 离线回网的养护副本点验

青徊园护的 12 人组用离线终端记录行道树养护。人工点验需要下载两份全量清单，逆序导出会干扰简单文本比较，终端记录较旧时也很难区分业务冲突与滞后修订。上游为主账和同一截止时点的终端快照，下游为负责补录和人工追查的核对员。

08:40 导出 ST-XH-1124 的主侧 48 条、终端 48 条；08:43 核对截止时点；08:45 设置每叶 16 个树号；08:47 比较根与分支摘要；08:50 定位 1234、1259、1260、1281；08:55 人工确认同代冲突；09:00 下载补录核查单；09:15 重跑仅顺序不同的东城对照。

每个叶区间由固定键域推导，输入顺序不影响摘要。叶以按树号排序的规范 JSON 计算 SHA-256，两个子摘要带类型前缀合并为父摘要。只对摘要不同的叶逐键比较。构树会读完双方输入，比较摘要的计数仅表示已建树后的递归比对开销。演练使用同一应用中提供的两份快照，MySQL 保存记录与证据，不连真实主从，也不自动修复终端数据。

# 巡养副本补传

资料的终端快照落库为副本 v1（`replica_versions` + `replica_entries`，全量物化、逐版不可变）。补传批次（`sync_batches`）声明截止时点、底版与分段数，截止时点须与资料的 `replica_epoch` 一致，底版不得超过当前版本。分段（`sync_segments`）只带改过的树：更新给整条记录，移除给 `{tree, removed: true}` 墓碑；分段按 `(batch_id, segment)` 去重，乱序到达。

收齐判定与切换在同一事务内完成：事务先锁资料行，因此并发的收口相互串行。收齐后先校验批内树号不重复、总量不超 2000，再与「底版之后已应用批次」的 touched 树号求交——相交（含墓碑）即整批退回，不写新版本；不相交则在当前最新版上并入本批改动，产出下一版本。两批同底且树号不相交时，后收齐者自动 rebase 到最新版，两批改动都保留。收齐前 `MAX(version)` 不动，新派单的点验照常读旧版。

点验派单（enqueue）时把当前副本版本钉进 `runs.replica_version`，worker 按该版本取全量条目替换 payload 中的 replica 再比对；结果 JSON 与 metrics 记录实际使用的版本，导出证据同源。无版本库的旧资料（快照非法）保持原行为：直接按 payload 执行，版本记空。
